# Twenty CRM and Mautic source audit

Audited 2026-10-11. This is a static source audit: no dependencies installed, application started, migration run, secrets read, deployment performed, or upstream file changed. Applicable repository instructions were read: Twenty `AGENTS.md` is a symlink to `CLAUDE.md`; Mautic has a root `AGENTS.md`.

## Decision

Use Twenty as the canonical CRM, reuse its existing agent/workflow/MCP/application capabilities, connect Ringee as an operational calling system through a small adapter, and connect Mautic as the marketing execution system through its APIs and signed webhooks. Do not fork either core to build the first integration. Twenty explicitly permits independently licensed applications using its published interfaces [T1]. Mautic provides the needed contact, segment, campaign, email, SMS and webhook primitives [M5–M10]. Neither source audit establishes a ready-made Twenty–Ringee–Mautic connector.

Start with a separate Mautic installation per business or isolation boundary. Twenty workspace scoping is implemented; Mautic Projects and owner permissions do not establish equivalent tenant isolation. A shared Mautic database with a `business_id` custom field would need a new, thoroughly verified authorization boundary, so it is not the minimum-change route.

## License boundaries and obligations

**Twenty — source-confirmed mixed license.** Root `LICENSE:2–9` says most code is AGPLv3; files beginning `/* @license Enterprise */` use the commercial terms instead; named toolkit/UI/application packages are MIT. The additional Application Exception at `LICENSE:20–51` covers published REST/GraphQL APIs, webhooks, manifests, runtime logic functions, front components and SDKs. An application that uses those interfaces without incorporating or modifying Twenty source may use its own terms. Official build-tool bundling does not extend AGPL to the application; libraries remain under their original terms [T1].

For modified AGPL-covered Twenty, retain license/notices and meet applicable source obligations; section 13 expressly requires a prominent source offer to remote users of the modified version (`LICENSE:599–609`). Redistribution requirements also apply. The [GNU license text](https://www.gnu.org/licenses/agpl-3.0.de.html) supports that network-source requirement. For MIT packages, retain the copyright and permission notice when distributing covered copies. Trademark rights are excluded from Twenty's exception (`LICENSE:48–51`).

**Enterprise is a material boundary.** Root `LICENSE:732–750` restricts production use of Enterprise-marked software to agreed terms and a valid Enterprise subscription for the appropriate hosts/seats; development/testing rights are separately described. A marker scan found 423 files under `twenty-server/src`, including row-level permission services, billing and enterprise AI-provider access. The row-level predicate service begins with the Enterprise marker [T8]. Source presence therefore does not mean permission to operate that feature in production. Custom AI-provider access code accepts billing mode, a valid Enterprise plan, or at most 25 distinct billable seats [T9]; this technical threshold is not a substitute for the root commercial terms. Exact intended production distribution and vendor entitlement must be reconciled before relying on Enterprise features.

**Mautic — source-confirmed GPL text with a labeling discrepancy.** `LICENSE.txt:5–8` grants GPL version 3 or later; line 18 says GPL v3, whereas root and app Composer manifests use `GPL-3.0` [M1]. Preserve the actual license text and notices in distribution; verify the precise SPDX interpretation for packaging rather than silently converting the label to `GPL-3.0-only`. GPL redistribution of covered modified software requires the applicable source/license terms; ordinary network use alone is not conveying under GPLv3. See the primary [GNU GPL text](https://www.gnu.org/licenses/gpl-3.0.de.html) and [GNU license FAQ](https://www.gnu.org/licenses/gpl-faq.html). No separate Enterprise-marked boundary was identified in the reviewed Mautic core/plugin source. Third-party and trademark notices still apply (`LICENSE.txt:20–24`).

## Minimum-change integration contract

1. **Canonical identity:** Twenty person/company/opportunity IDs remain authoritative. Store mappings keyed by `(business/workspace ID, Twenty object ID)` to Ringee contact/call IDs and Mautic contact/company IDs. Mautic may retain a custom Twenty-ID field, but the adapter's mapping and uniqueness policy must prevent duplicate creation. Email/phone changes must not create a second canonical person automatically.
2. **Owned fields:** Twenty owns business identity, sales ownership and lifecycle. Ringee owns call lifecycle, recording/transcript references and operational disposition. Mautic owns campaign participation, engagement and marketing DNC state. Copy summaries and provider IDs into Twenty custom fields/objects via published API or a Twenty application. Do not let every system overwrite every field.
3. **Events:** Twenty record changes go through a signed webhook or workflow HTTP action to the adapter. Adapter upserts the authorized Mautic audience record and prepares an operational Ringee call job. Ringee events return call outcome data to Twenty; the detailed Ringee endpoint/auth capability is outside this audit and must be supplied by its audit. Mautic engagement/DNC webhooks update mapped CRM fields and suppress future sends. A Mautic campaign webhook can request an adapter action, but the adapter must validate it before execution.
4. **Durability:** Acknowledge webhook receipt after recording the event; retry asynchronously with bounded exponential backoff and dead-letter handling. Deduplicate by stable provider event ID where available, otherwise by carefully defined business operation key; maintain operation status and source timestamps. Add replay protection for Twenty's timestamp/nonce and a receiver-side strategy for Mautic, whose inspected signature lacks an explicit timestamp. Prevent bidirectional echo loops with source and field ownership.
5. **Action gates:** Reuse Twenty native agents to propose CRM updates, drafts or call/campaign actions. Store approval and release state for operational actions; the adapter checks approver/business/scope, current suppression state, recipient cap and available spend budget immediately before execution. Treat Mautic DNC as suppression data, not as complete proof of consent. Removing DNC or adding a person to a sendable segment is a controlled action.
6. **Extension route:** First use external API/webhook adapters. If UI/actions/custom objects are needed inside Twenty, use its MIT SDK and application manifests/logic functions/front components under the explicit Application Exception [T1, T4]. Narrow the sample role: the hello-world role grants broad read/update/soft-delete permissions and should not be copied as production least privilege. Use Mautic's IntegrationsBundle interfaces/plugin framework only when native campaign UI/actions are required; no Twenty/Ringee class was found in the bundled CRM integrations [M14].

## Open items before implementation or production

- **Release/licensing:** Match audit commits to selected tagged releases and artifacts. Determine Twenty Enterprise entitlement needed for intended features and resolve custom AI-provider licensing versus the technical 25-seat gate. Retain exact notices, MIT notices and applicable source offers.
- **Runtime capability:** Verify Twenty's selected release exposes MCP, agents, app platform and approvals with required feature flags/model credentials; prove Mautic APIs/auth and provider transports on its selected release. This audit ran no health checks or integration tests.
- **Isolation:** Confirm business/workspace inventory and provision-per-business Mautic assumption. Test cross-workspace credentials, mappings, unauthorized approvals, callbacks and deletion paths. Shared infrastructure still needs separate DB/provider configuration boundaries.
- **Operational contract:** Ringee audit must confirm supported contact/call APIs and signed event delivery. Agree recipient/suppression field ownership, approval roles, external spend ceilings, provider accounts and contact-to-call concurrency.
- **Capacity/recovery:** Measure queue lag, campaign/segment work, Redis consumption, DB/storage growth and restoration. Native source minima do not establish combined-stack sizing or SLA.

The concrete next artifact is a versioned mapping/event/approval contract and an adapter skeleton with fixture-based verification of signing, deduplication, workspace routing, suppression, spend checks and writeback. No upstream patches are required for that step.
